# Academic similarity

Two schools are academically almost perfectly similar if they offer the same
degrees in the same subjects, both undergrad and grad, and the number of
students getting those degrees is similar both per-degree and in total. They
differ academically as subjects offered, degrees attained, degree proportion,
and overall size of undergrad and grad population differ.

This is the **first of what will be a family of similarity indexes** (see
"Why not generalize the table yet" below) — distinct from the existing
`peer_network` table, which measures overall institutional-profile similarity
(enrollment size, admit rate, tuition, instructional spending), not academic
program mix.

## Data source: `completions_by_field`

Loaded in `scripts/etl/load-year.ts` from IPEDS's raw `C{year}_A` table
(degrees conferred by CIP code):

- **6-digit CIP code** granularity (e.g. `51.3801`), not the coarser 2-digit
  CIP family — checked at ~72k rows/year (2-digit) vs ~145k rows/year
  (6-digit) for one year; 6-digit is barely more expensive to store and far
  more faithful to "same subject" than lumping, e.g., all of Health
  Professions (CIP 51) together.
- **First major only** (`MAJORNUM = 1`) — avoids double-counting students
  with a double major.
- **Leaf award levels only**: `{3, 5, 7, 17, 18, 19}` (Associate's,
  Bachelor's, Master's, Doctor's-research/professional/other). The raw table
  also contains CIP-family/subfamily rollup rows (`CIPCODE = '01'`,
  `'01.09'`, etc. alongside the leaf `'01.0999'`) and non-leaf `AWLEVEL`
  "total" pseudo-codes (12, 13, 14, 15) — including those would multiply-
  count everything under them.
- Restricted to degree-granting institutions only (same `DEGGRANT` gate as
  everything else — see `.claude/skills/institution-scope`).

**Memory note:** the raw `C{year}_A` table is huge (1.4–1.7M rows, ~30
demographic-breakdown columns) — `mdb-reader`'s `getData()` materializing all
of it OOM'd a 4GB+ Node heap. Fixed by projecting to only the 5 needed
columns via `getData({ columns: [...] })` in `tableOrNull()`. Column casing
(`UNITID` vs `unitid`) is inconsistent across tables *and years* — resolve
requested column names case-insensitively against the table's actual columns
before projecting, the same way table names are already resolved.

## The formula

Computed in `scripts/etl/materialize.ts` (in JS, not SQL — a sparse cosine
similarity over each institution's subject×level mix isn't a plain
join/aggregate the way the other materialized tables are):

1. **Composition distance** — captures "same subjects in the same degrees,
   proportionally," independent of size. For each institution, build a share
   vector over `(cip_code, award_level)` keys (each institution's own
   completion counts normalized to sum to 1). Cosine similarity between two
   institutions' share vectors, converted to a proper distance:
   `compositionDistance = sqrt(2 * (1 - cosineSim))`.
2. **Size distance** — captures "overall size of undergrad and grad
   population differ." Sum each institution's completions into an
   undergrad total (Associate's + Bachelor's) and a grad total (Master's +
   all Doctor's), z-normalize each within the same institution_type cohort,
   then `sizeDistance = sqrt(zUndergrad² + zGrad²)`. Sizing is based on
   *completions*, not enrollment headcount — consistent with the "students
   getting those degrees" framing, and self-contained within the same data
   source.
3. **Combined**: `academicDistance = sqrt(compositionDistance² + sizeDistance²)`.
   This is a first-cut heuristic (equal-ish weighting of shape vs size, no
   empirical tuning yet) — revisit the weighting if it doesn't match
   intuition once surfaced somewhere.

Peers are drawn only from the same `institution_type` cohort in the same
year (college-vs-college, etc.), same restriction as `peer_network`.

## Storage: `academic_similarity`

Same shape as `peer_network`: `(unitid, year, rank, peer_unitid, distance)`,
top 12 per institution per year. Precomputed, not queried live — see
`.claude/skills/precompute-over-live-query`. **Must be regenerated by
`materialize.ts` after every backfill**, same as `nationwide_trends` and
`peer_network`.

## Why not generalize the table yet

With only two similarity indexes (`peer_network`, `academic_similarity`),
this deliberately stays as two separate same-shaped tables rather than one
generalized `similarity_index(index_name, ...)` table — avoiding the
abstraction until there's a third index to justify it (rule of three). If/
when a third index is added, that's the right moment to fold these into one
parameterized table and migrate both existing ones into it.

## Not yet exposed in the UI

As of this writing, `academic_similarity` is computed and stored but not
queried by any page — `getPeers()` in `src/db/queries.ts` still only reads
`peer_network`. Surfacing academic similarity (its own view, a toggle next
to the existing peer network, etc.) is a separate, not-yet-made decision.
